B+tree index, từ câu query tới từng page trong RAM

Ghi chú học tập trên lộ trình lên senior backend. Mỗi khái niệm đi kèm một mô phỏng để bấm thử: cây split ra sao, page 8KB bên trong trông thế nào, và vì sao một query nhanh hay chậm.

Sân chơi B+tree

Mỗi node chứa tối đa 3 key để dễ thấy split. Màu vàng là page vừa bị ghi, màu xanh dương là đường đi khi tìm, màu xanh lá là leaf chứa key.

01

B-tree được dùng ở đâu

Gần như mọi database dùng biến thể B+tree: data hoặc con trỏ tới row chỉ nằm ở leaf, và các leaf nối với nhau thành danh sách liên kết hai chiều.

DatabaseIndex dùng B+tree
PostgreSQLIndex mặc định, PRIMARY KEY, UNIQUE, composite, expression index, partial index
MySQL InnoDBClustered index (chính là PK, leaf chứa nguyên row) và mọi secondary index (leaf chứa giá trị PK)
Oracle, SQL Server, SQLiteIndex mặc định. SQLite lưu cả table dưới dạng B-tree
MongoDB (WiredTiger)Index mặc định

Không dùng B-tree: Hash, GIN (full-text, JSONB), GiST/R-tree (geo), BRIN, LSM-tree (RocksDB, Cassandra).

Khi nào B-tree hiệu quả

  • Equality WHERE id = 42 và range >, <, BETWEEN
  • ORDER BY, GROUP BY trên cột đã index, không cần bước sort
  • MIN/MAX, prefix LIKE 'abc%'
  • Composite index theo leftmost prefix: (a, b, c) dùng được cho a, a+b, a+b+c, không dùng được cho b đứng một mình

Khi nào không hiệu quả

  • LIKE '%abc', hoặc bọc cột trong hàm như LOWER(email) mà không có expression index
  • Cột cardinality thấp như status
  • Query trả về phần lớn bảng: planner sẽ chọn Seq Scan
02

Page, fan-out và chiều cao

Đơn vị lưu trữ là page, không phải từng row. Mỗi node của cây là một page.

DatabasePage mặc địnhĐổi được không
PostgreSQL8KBChỉ khi compile lại (BLCKSZ)
MySQL InnoDB16KBinnodb_page_size, chỉ lúc khởi tạo instance
SQL Server, Oracle8KBOracle qua db_block_size
SQLite4KBQua PRAGMA
  • Mọi page trong một DB có cùng kích thước, nên vị trí page N trên disk là N × 8KB, và mỗi frame trong RAM vừa khít một page.
  • Không dùng được trọn 8KB: header 24 byte, special space 16 byte, mỗi entry tốn thêm pointer 4 byte. Một entry index tối đa khoảng 1/3 page (~2.7KB).
  • Fan-out (số con mỗi node) lớn, vài trăm, nên cây rất thấp. Key càng nhỏ, fan-out càng lớn.

Thử đổi kiểu key và số row để thấy chiều cao cây thay đổi thế nào:

Ước lượng kích thước indexPostgreSQL B-tree
Entry / page
Chiều cao cây
Page đọc để tìm 1 key
Kích thước index (ước tính)

Với bigint, mỗi entry khoảng 20 byte nên một page chứa khoảng 400 entry: 3 tầng đủ cho ~64 triệu row, 4 tầng cho ~25 tỷ row. Đó là lý do tìm một row trong hàng trăm triệu row chỉ tốn 3–4 lần đọc page.

03

Split: cây lớn lên thế nào

Khi một page đầy, DB không ghi tràn sang page bên cạnh. Key mới phải nằm đúng vị trí theo thứ tự, nên page bị split:

  1. Tạo page mới.
  2. Chuyển khoảng một nửa số entry sang page mới.
  3. Đẩy separator key lên parent.
  4. Nếu parent cũng tràn, parent split tiếp. Split lan tới root thì tạo root mới và cây cao thêm một tầng.

Hai loại split khác nhau ở chỗ separator key:

  • Leaf split: copy lên. Key vẫn ở lại leaf vì leaf giữ data thật.
  • Internal split: move lên. Internal node chỉ là biển chỉ đường, nên key giữa rời hẳn tầng đó.

Internal node có n key thì có n + 1 con. Mỗi key là ranh giới giữa hai con nằm cạnh nó: [6 | 8 | 10] có 4 con là <6, 6–8, 8–10, ≥10.

Lỗi hay gặp: quên cập nhật parent sau khi split. Separator trong parent và nội dung leaf phải khớp nhau, nếu không lần tìm sau sẽ đi sai leaf và không thấy key. Mỗi lần split, luôn hỏi: parent thay đổi thế nào?

B-tree cao lên từ đỉnh, không mọc dài xuống đáy. Mọi leaf luôn cùng độ sâu, nên tìm bất kỳ key nào cũng tốn số bước như nhau, O(log n).

Split chia đôi để mua trước chỗ trống: lần split tốn kém, nhưng các insert tiếp theo vào khoảng đó chỉ ghi 1 page.

Góc nhìn senior: điểm tách không phải lúc nào cũng ở giữa

  • Key tăng dần (auto-increment, UUIDv7): khi split leaf ngoài cùng bên phải, DB giữ leaf cũ gần đầy và mở leaf mới gần trống. Index gọn, gần 100% đầy.
  • Key ngẫu nhiên (UUIDv4): split xảy ra rải rác khắp cây, leaf chỉ đầy 50–70%. Index phình to, tốn RAM, buffer pool bị churn.
  • fillfactor (B-tree PostgreSQL mặc định 90) chừa sẵn chỗ khi build index để giảm split.
  • Trước khi split, PostgreSQL thử dọn chỗ: xoá entry đã chết và deduplication (từ PG13) gộp các entry cùng key.
04

Bên trong một page

Leaf phải giữ key theo thứ tự để binary search. Nhưng nếu xếp tuple liền nhau theo thứ tự, mỗi lần chèn vào giữa phải dời toàn bộ dữ liệu phía sau. Cách giải là slotted page, chia page làm hai vùng mọc ngược chiều nhau:

  • Mục lục (line pointer): ở đầu page, mỗi pointer 4 byte, luôn sắp xếp theo key.
  • Tuple (key + TID): ở cuối page, ghi nối tiếp theo thứ tự đến trước, không bao giờ phải dời khi insert.

Như một cuốn sổ: ghi nội dung ở trang cuối theo thứ tự tuỳ ý, và giữ một mục lục đã sắp xếp ở trang đầu.

Pointer "tăng dần" nghĩa là tăng theo giá trị key, còn địa chỉ chúng trỏ tới thì lộn xộn. Khi hai vùng gặp nhau, page hết chỗ và lần insert sau gây split. Header còn chứa LSN: vị trí trong WAL của lần sửa gần nhất.

Layout này trong RAM và trên disk giống hệt nhau. Buffer pool copy nguyên khối 8KB, không chuyển thành object nào khác.

05

Buffer pool: index nằm trong RAM thế nào

Không có chuyện load cả index vào RAM. Page chỉ được đọc lên khi query cần đến (lazy). Con trỏ con trong index là page number, không phải địa chỉ RAM, nên mỗi bước đi xuống cây phải hỏi buffer pool: page số X đang ở đâu?

06

Vòng đời INSERT rồi SELECT

Một INSERT ghi gì và ghi ở đâu, rồi một SELECT range đọc lại nó ra sao. Chú ý luật WAL trước, data page sau.

  • Commit chỉ cần fsync WAL. Data page vẫn dirty trong RAM, được background writer, checkpoint, hoặc eviction ghi xuống sau.
  • Trước khi flush một page, WAL phải đã nằm trên disk tới ít nhất LSN trong header page đó. Crash thì replay WAL.
07

Trace một query thật

Bảng orders 50 triệu row (~6.5GB), index (user_id, created_at) ~1.6GB, cao 3 tầng.

CREATE INDEX idx_orders_user_created ON orders (user_id, created_at);

SELECT id, total FROM orders
WHERE user_id = 42 AND created_at >= '2026-10-01'
ORDER BY created_at
LIMIT 20;

Trong 24 lần truy cập page, chỉ 5 là index. Heap fetch mới là phần đắt, vì đơn của một user nằm rải rác khắp bảng. read chỉ có nghĩa là không có trong shared_buffers, page vẫn có thể nằm trong OS page cache. Bật track_io_timing để thấy thời gian I/O thật.

Trên InnoDB, leaf secondary index chứa PK, nên mỗi row phải duyệt thêm cây clustered index (khoảng 3 page thay vì 1). Covering index còn quan trọng hơn ở MySQL.

08

Index Only Scan và cái giá của SELECT *

Nếu mọi cột query cần đều có trong index, DB trả kết quả ngay từ leaf mà không ghé heap. Đó là Index Only Scan. Chỉ cần thêm một cột không có trong index là mất khả năng này.

CREATE INDEX idx_cov ON orders (user_id, created_at) INCLUDE (total, id);
Cùng một index, hai câu SELECT
-- Query A
Index Only Scan using idx_cov on orders
  Heap Fetches: 0
  Buffers: shared hit=4

-- Query B
Index Scan using idx_cov on orders
  Buffers: shared hit=5 read=19
Dễ nhầm: PostgreSQL leaf entry chỉ chứa key và TID, không tự có PK. Query SELECT id, total cần INCLUDE (total, id), chỉ INCLUDE (total) là chưa đủ. InnoDB thì khác: secondary index tự chứa PK.

Index không chứa thông tin MVCC, nên Index Only Scan chỉ bỏ qua heap khi visibility map đánh dấu page là all-visible. Nếu Heap Fetches lớn, cần VACUUM chứ không phải sửa index.

Chi phí tính theo row, không theo cột

Một row nằm trọn trong một page, các cột nằm liền nhau. Đọc thêm cột thường của cùng row gần như miễn phí. Bước nhảy chi phí là từ 0 lên 1 heap fetch cho mỗi row. Ngoại lệ là cột lớn bị TOAST:

Covering index có giá

Index to hơn, tốn RAM hơn, mỗi lần ghi tốn hơn. Ở PostgreSQL, đưa cột hay bị UPDATE vào index (kể cả qua INCLUDE) sẽ phá HOT update. Chỉ cover cho query thật sự nóng, với cột ít thay đổi.

09

Heap và MVCC

Trong PostgreSQL, heap là nơi lưu chính các row của table (không phải cấu trúc min-heap, cũng không phải heap memory). Index chỉ là cấu trúc phụ trỏ vào nó.

  • Mỗi table là một file gồm các page 8KB, cũng là slotted page.
  • "Heap" nghĩa là một đống: row không được sắp xếp theo cột nào, đặt vào page còn chỗ (Free Space Map chỉ đường).
  • Mỗi row có địa chỉ TID = (page, slot), chính là cột ẩn ctid.
  • Header của row có xmin (transaction tạo row) và xmax (transaction xoá hoặc thay thế row).

Điểm quan trọng nhất: UPDATE không ghi đè row cũ.

PostgreSQLMySQL InnoDB
Row nằm ở đâuHeap, không sắp xếpLeaf của clustered index, xếp theo PK
Index trỏ tớiTID (địa chỉ vật lý)Giá trị PK, rồi tra tiếp cây PK
Phiên bản cũ khi UPDATETrong heap, chờ VACUUMUndo log, row được sửa tại chỗ

Vì sao senior phải hiểu heap

  • Bloat: UPDATE/DELETE liên tục mà autovacuum không theo kịp thì dead tuple chất đống, bảng phình và scan chậm dần.
  • Transaction mở lâu chặn VACUUM dọn mọi phiên bản mà nó có thể còn cần.
  • Bảng update nhiều: hạn chế index trên cột hay bị update để giữ HOT, đặt fillfactor 80–90 để chừa chỗ.
  • Heap không xếp theo user_id, nên range scan qua index đọc rải rác nhiều page.
SELECT ctid, id, total FROM orders WHERE id = 9001;   -- (0,2)
UPDATE orders SET total = 400000 WHERE id = 9001;
SELECT ctid, id, total FROM orders WHERE id = 9001;   -- (0,3): phiên bản mới

SELECT n_live_tup, n_dead_tup, n_tup_upd, n_tup_hot_upd, last_autovacuum
FROM pg_stat_user_tables WHERE relname = 'orders';

Checklist senior và bài tập

Mid-level biết "đánh index cho cột hay query". Senior lập luận được về cái giá và đo được, không đoán:

  • Write amplification: mỗi index thêm một lần duyệt cây, có thể thêm split, thêm WAL cho mỗi INSERT/UPDATE.
  • Key nhỏ, tăng dần cho index gọn. UUIDv4 làm index phình, nên dùng UUIDv7/ULID.
  • Đọc được EXPLAIN (ANALYZE, BUFFERS): shared hit là cache hit, read là miss.
  • Working set có vừa RAM không: OLTP mà hit ratio dưới ~99% là dấu hiệu cần điều tra.
-- Cache hit ratio theo từng index
SELECT indexrelname, idx_blks_hit, idx_blks_read,
       round(idx_blks_hit * 100.0 / nullif(idx_blks_hit + idx_blks_read, 0), 2) AS hit_pct
FROM pg_statio_user_indexes
ORDER BY idx_blks_read DESC;

SELECT pg_size_pretty(pg_relation_size('your_index'));

Bài tập thực hành

Seq Scan, Index Scan, Index Only Scan

Tạo bảng 10 triệu row. So sánh EXPLAIN (ANALYZE, BUFFERS) của cùng một query với ba loại scan.

Cache lạnh và cache nóng

Restart PostgreSQL, chạy một query hai lần liên tiếp với BUFFERS. So sánh shared read và shared hit. Lần đầu có thật sự đọc disk không, hay OS page cache đã đỡ?
